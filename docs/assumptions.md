# Допущения и разрешение расхождений

1. Командная архитектура имеет приоритет над техническими названиями в приложенном задании. Сохранены UNDERWRITER, COUNTER_OFFER, SIGNING, ISSUED, /underwriter и формат ошибок RFC 7807. Не добавлены параллельные /bank и DISBURSED.
2. BPMN и существующая стейт-машина совмещают подтверждение подписи и симуляцию выдачи в SIGNING → ISSUED. UI прямо обозначает оба действия в одной кнопке. Принятие оффера — отдельная команда. Отдельный шаг SIGNED → DISBURSED потребует согласованного изменения BPMN, справочника статусов и API и здесь не вводится.
3. Сбой внешней проверки ведёт на ручную проверку, как требуют BPMN и docs/design/principles.md: конвейер всегда идёт `EXTERNAL_CHECK → SCORING`, затем `SCORING → MANUAL_REVIEW` с правилом `EXTERNAL_UNAVAILABLE`, если нет стоп-фактора по доступным источникам (стоп-фактор приоритетнее сбоя другого источника). Прямого перехода `EXTERNAL_CHECK → MANUAL_REVIEW` нет. Сбой не становится кредитным отказом. Обновление профиля при недоступном ЕГРЮЛ возвращает 503. Это осознанное отличие от требования вернуть 503 при подаче.
4. Вместо BackgroundTasks используется синхронный ограниченный конвейер в одной транзакции с подачей. Искусственных задержек нет. Клиент получает итог и полный таймлайн без ожидания анимации промежуточных этапов. При необработанном техническом исключении откатываются состояние, аудит, решение и проверки; черновик остаётся редактируемым.
5. Сохранён WireMock из C4. Нового сервиса FastAPI для моков нет. HTTP-клиент на стандартной библиотеке, без изменения lock-зависимостей backend.
6. Командный запрет менять закреплённые ИНН соблюдён. Значения из seed — синтетические идентификаторы длиной 10/12 цифр, они не проходят полноценную проверку контрольных цифр ФНС. Контрольные цифры не заявляются проверенными. Для регистрации по своему ИНН (сессия 4) контрольные числа ФНС проверяются в `domain/inn.py`; seed-ИНН и `7701000099` пропускаются явным списком исключений `SEED_INNS`, остальные обязаны пройти проверку.
7. Возраст компании считается от `AS_OF_DATE` (env) или от сегодняшней даты по Europe/Moscow; `snapshot_date` политики — только дата версии. В тестах `AS_OF_DATE=2026-10-23`. Для client_manual дата регистрации 2026-01-23; исход сценария не зависит от даты проверки (балл 50–60). Уже существующие компании seed не перезаписывает; оценка использует дату из снимка ЕГРЮЛ.
8. Контрпредложение автоматически возможно только при score ≥ 70. Ошибочный пример с 64 из командных материалов заменён воспроизводимым сценарием со 100 баллами и лимитом 6 млн ₽. Баллы не являются вероятностью дефолта.
9. Ставка = ключевая ставка ЦБ + спред продукта + риск-надбавка (одна функция `domain/pricing.py` для автооффера, ручного решения и каталога). Ключевая ставка в `policy.yaml`: 14,0% на 2026-10-23 (решение Совета директоров Банка России); значение нужно сверить с cbr.ru на дату проверки и при необходимости переопределить `KEY_RATE_PCT` / `KEY_RATE_DATE`. Спреды и риск-надбавка синтетические. Runtime не обращается к ЦБ. Каталог показывает «от X%» (без надбавки), `dim_credit_product.rate_nval` заполняется той же функцией при seed.
10. Проверка рассмотрения хранится в существующих credit_decision, decision_factor и external_check. Структурированный снимок (версия политики, asOfDate, входы с источниками, проверки, факторы с maxPoints, лимит, ставка) лежит в `credit_decision.decision_snapshot`; `comment_desc` — только внутренний комментарий андеррайтера, клиент его не получает, а видит `decisionExplanation`. Отдельной дублирующей CheckRun-таблицы нет.
11. Подтверждённый источник (ФНС для выручки, БКИ для долга) приоритетнее анкеты; значение клиента, включая ответ на дозапрос, используется только при пустом ответе источника. Расхождение анкеты с источником больше 20% (`data_mismatch_pct`) отправляет заявку на `MANUAL_REVIEW` (правило и фактор `DATA_MISMATCH`). Выручка только со слов клиента урезает лимит коэффициентом 0,5 (`client_declared_limit_factor`). Нулевое значение отличается от отсутствующего. Профиль компании изменяется только по отдельной команде обновления.
12. Идемпотентность submit сохраняет прежний глобальный ключ заявки и возвращает её текущее представление. Для missing-info, offer/accept и sign ключ scoped по пользователю и операции, хранятся хеш тела и исходный ответ. Заголовок у этих команд необязателен для обратной совместимости; новый UI его передаёт. Повтор без ключа отклоняется проверкой состояния, повторной выдачи не происходит.
13. Моки детерминированы по 9-й цифре 10-значного ИНН (10-й цифре 12-значного): стабы `*-digit-N.json` (priority 8) отвечают на любой ИНН своим сценарием, seed-стабы (priority 5) приоритетнее, общий fallback (priority 10) остаётся запасным. Одинакового профиля для всех ИНН больше нет. Реальные интеграции, SMS, документы, ЭЦП и LLM отсутствуют.

Сессия 2.

- Повторная проверка источников (`recheck`) доступна андеррайтеру только в `MANUAL_REVIEW` и возвращает заявку в `EXTERNAL_CHECK`; прежние проверки и решения остаются в истории, актуальными считаются последние.
- Отзыв заявки (`WITHDRAWN`) возможен из `DRAFT`, `NEEDS_INFO`, `MANUAL_REVIEW`. После решения банка (`APPROVED`/`COUNTER_OFFER`) клиент отказывается через `DECLINED_BY_CLIENT`, дублирующего перехода нет.
- Срок оффера 30 дней, срок ответа на запрос данных 14 дней (`OFFER_TTL_DAYS`, `INFO_REQUEST_TTL_DAYS`). Планировщика нет: просрочка обнаруживается лениво в начале команд `offer/accept`, `offer/decline`, `missing-info`, `sign` либо скриптом `app.scripts.expire_stale`. Принятый оффер (`SIGNING`) не истекает. Старые офферы и запросы без срока (`NULL`) не истекают. «Сейчас» берётся из `app.core.clock.now()`.
- Подбор продукта детерминированный: `matchScore` = соответствие цели и продукта из `recommendation.yaml` минус штрафы за сумму и срок вне диапазона продукта и нетипичный срок; `recommended` получает только лучший продукт, подходящий по сумме и сроку и набравший не меньше порога. Это совет по выбору продукта, не кредитное решение: итог по заявке считает движок решений.

Сессия 3.

- Внешние проверки (ЕГРЮЛ, ФНС, БКИ) опрашиваются параллельно в потоках с общим бюджетом `EXTERNAL_CHECKS_BUDGET_SECONDS` (3 с по умолчанию), ретраи (до 3 попыток по 0,8 с) идут внутри бюджета. Записи `external_check` создаются в основной сессии. Осознанное ограничение: HTTP-вызовы остаются внутри транзакции под `SELECT FOR UPDATE` строки заявки, так как конвейер атомарен с подачей; блокировка держится не дольше бюджета.
- JWT-секрет: если `JWT_SECRET` пуст, равен прежнему демо-значению или короче 32 символов, при первом старте создаётся случайный (`secrets.token_urlsafe(48)`), сохраняется в `/app/data/jwt_secret` (named volume `jwtdata`) и читается при следующих стартах; в логе WARNING без значения. Без доступного файла секрет живёт только в памяти. Токены, подписанные старым демо-секретом, отклоняются (401).
- Ограничение попыток входа (5 неудач за 5 минут на связку логин + IP, затем 429 `TOO_MANY_REQUESTS` с `Retry-After`) хранится в памяти одного процесса: при нескольких воркерах или репликах счётчики не общие, после перезапуска сбрасываются.
- Код подписи в `signHint` возвращается только при `DEMO_MODE=true` (по умолчанию включён для удобства проверки).

Сессия 4.

- Регистрация `POST /auth/register` создаёт компанию из ответа ЕГРЮЛ и клиента; при недоступном ЕГРЮЛ — 503 `EGRUL_UNAVAILABLE`, ничего не создаётся. Компания с отказным сценарием (цифра 8, не действует) регистрируется, отказ даёт скоринг. Прежнее допущение «только seed-аккаунты» снято.
- Лимит регистрации — отдельный от входа: все попытки с IP (успешные тоже) считаются в том же окне, `REGISTER_MAX_ATTEMPTS` (20). Лимит входа в 5 неудач не подошёл: он не защищает БД от спама успешными регистрациями и мешает проверить все 10 сценариев подряд. Счётчики в памяти процесса.
- Отрасль из ЕГРЮЛ в `company` не сохраняется (колонки нет, схема не менялась): она берётся из снимка ЕГРЮЛ при скоринге.
- Цифра 5: дата регистрации в стабе считается шаблоном WireMock `now − 9 months`, поэтому при штатном `AS_OF_DATE` (сегодня) возраст всегда 9 месяцев и исход не меняется. При жёстко заданном `AS_OF_DATE` в прошлом возраст станет отрицательным (стоп-фактор `YOUNG_COMPANY`).
