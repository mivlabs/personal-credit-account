# Целевые показатели

Цели — это ориентиры, которые мы предлагаем принять для пилота и промышленной версии. Они не следуют из нормативов и
из данных банка, которых у прототипа нет, поэтому у каждой цели указано обоснование и способ измерения. Замеры — это
фактические числа с условиями; где замера нет, так и написано.

## Условия замеров

Дата 2026-10-24. Windows 10, 4 ядра. PostgreSQL 16 и WireMock 3.13.2 в Docker (`docker compose up -d db mocks`),
API — локальный процесс `uvicorn` (один воркер) на чистой БД с seed. Клиент — [`scripts/measure.py`](../scripts/measure.py),
один поток, запросы друг за другом, время включает локальный HTTP. Моки работают на той же машине и отвечают за
единицы миллисекунд, поэтому цифры показывают собственные затраты приложения, а не сеть и реальные внешние сервисы.
Память — `docker stats --no-stream` на поднятом в простое стеке `docker compose up` (4 контейнера). Повторить замер:

```bash
docker compose -f docker-compose.yml -f docker-compose.override.example.yml up -d db mocks
cd backend && uv run uvicorn app.main:app --port 8010 &   # с DATABASE_URL на отдельную БД и MOCKS_BASE_URL
python scripts/measure.py --base-url http://127.0.0.1:8010
```

## Показатели

| Показатель | Цель | Обоснование цели | Как измеряется | Замер на демо-стенде |
|---|---|---|---|---|
| Время автоматического решения (от `POST /submit` до итогового статуса) | p95 ≤ 5 с; с учётом бюджета внешних проверок 3 с — не больше 3 с на опрос ЕГРЮЛ/ФНС/БКИ плюс обработка не дольше 2 с | Клиент ждёт ответ на экране, а подача синхронная. Бюджет 3 с (`EXTERNAL_CHECKS_BUDGET_SECONDS`) ограничивает самое долгое звено, остальное — запись в БД и скоринг | Время ответа `POST /applications/{id}/submit` (возвращает уже итог); на банковской стороне — разница времени переходов `SUBMITTED` и итогового статуса в аудите | Источники отвечают быстро: p50 / p95 / max, мс — одобрение 101 / 126 / 173 (20 заявок), контроффер 104 / 214 / 244 (20), отказ по стоп-фактору 88 / 183 / 188 (20), БКИ 503 с ретраями 116 / 151 / 151 (5). Источник отвечает 2 с (ИНН с 9-й цифрой 7): ≈ 2,7 с (3 подачи). Бюджет 3 с исчерпанным не мерился |
| Время ответа API на чтение | p95 ≤ 300 мс | До 1 с пользователь не теряет нить действий ([Nielsen, «Response Times: The 3 Important Limits»](https://www.nngroup.com/articles/response-times-3-important-limits/)); 300 мс оставляют запас на сеть и на экраны, где запросов несколько | p95 по последовательным запросам из `scripts/measure.py`; в промышленной версии — серверная метрика | p50 / p95 / max, мс (по 200 запросов): `/health` 8 / 11 / 29, `/products` 11 / 20 / 49, `/companies/me` 10 / 24 / 44, `/applications/{id}` 19 / 27 / 41, `/underwriter/queue` 21 / 41 / 172. Первый запрос после старта процесса бывает медленнее (в одном прогоне до 1,4 с на подачу) |
| Доля автоматических решений (без участия андеррайтера) | ≥ 70% заявок | Гипотеза для калибровки. Ручная проверка нужна пограничным баллам 40–69 и сбоям источников; если автоматически закрывается меньше большинства потока, кабинет не снимает нагрузку с андеррайтеров. Точное значение определяется по портфелю банка | Доля заявок, не прошедших через `MANUAL_REVIEW`, среди завершённых; считается по аудиту | Не измерялось на потоке: потока нет. На десяти сценариях по цифре ИНН 7 из 10 заканчиваются без андеррайтера (в т. ч. запрос данных) — это состав тестового набора, а не оценка доли в реальности |
| Время ручного решения андеррайтером | 90% заявок в `MANUAL_REVIEW` решены в течение 1 рабочего дня | Бизнес-цель: клиенту малого бизнеса нужен ответ быстрее, чем в отделении; срок задаёт банк, цифра — предложение для пилота | Разница времени перехода в `MANUAL_REVIEW` и ручного решения по аудиту (`loan_application_aud`) | Не измерялось: ручные решения в прототипе принимаются людьми на демонстрации, таймера и SLA в системе нет |
| Доступность | Пилот: 99,5% в рабочие часы; промышленная версия: по требованиям банка к кредитному каналу | Пилот допускает окна обслуживания; для промышленной версии цифру задаёт банк и она зависит от архитектуры ([`production.md`](production.md)) | Внешний мониторинг `GET /health`, доля успешных проверок за период | Не измерялось: стенд локальный. Есть healthcheck у каждого контейнера и проверка БД в `/health` |
| Устойчивость к сбою внешнего источника | 100% заявок при сбое источника не получают технический отказ: уходят на ручную проверку | Недоступность ЕГРЮЛ, ФНС или БКИ — не причина кредитного отказа клиенту | Сценарии «БКИ 503» и «БКИ медленный» в интеграционных тестах | Проверено тестами на WireMock (ИНН с 9-й цифрой 7 и 9, `client_timeout`): итог `MANUAL_REVIEW` с правилом недоступности источника |
| Прозрачность решения | 100% автоматических решений имеют сохранённый снимок (входы с источниками, факторы, лимит, ставка) | Клиент и андеррайтер должны видеть, почему принято решение; нужен для разбора спорных случаев | Наличие `credit_decision.decision_snapshot` у каждого AUTO-решения | По конструкции: снимок пишется в той же транзакции, что и решение ([`decision-policy.md`](decision-policy.md)) |
| Повторная выдача | 0 | Деньги нельзя выдать дважды | Ограничение `UNIQUE(disbursement.application_id)` и идемпотентные команды | По конструкции на уровне БД; конкурентные повторы покрыты интеграционными тестами |
| Ресурсы стенда | В простое весь стек ≤ 1 ГиБ ОЗУ, образы ≤ 2 ГБ | Стек должен подниматься на обычном ноутбуке рядом с остальными задачами | `docker stats --no-stream`, `docker images` | ОЗУ в простое: api 69 МиБ, db 41 МиБ, mocks 135 МиБ, web 4 МиБ, всего около 250 МиБ. Образы: api 316 МБ, web 94 МБ, PostgreSQL 420 МБ, WireMock 462 МБ, всего около 1,3 ГБ |
| Пропускная способность под нагрузкой | Определяется при проектировании промышленной версии | Нужны данные о потоке заявок банка | Нагрузочный тест с параллельными пользователями | Не измерялось: замеры однопоточные. Один поток даёт порядка 10 подач в секунду при p50 ≈ 100 мс, но это не нагрузочный тест |

## Что важно при чтении замеров

- Замеры показывают затраты приложения. Реальные ЕГРЮЛ, ФНС и БКИ отвечают дольше моков; для этого и нужен бюджет 3 с.
- HTTP-вызовы к источникам в прототипе идут внутри транзакции подачи (см. [`assumptions.md`](assumptions.md)): при большом
  потоке они держат соединения БД. В промышленной версии конвейер выносится в очередь ([`production.md`](production.md)).
- Цели по доле автоматических решений и по времени ручного решения — предложения для пилота, их нужно согласовать
  с кредитной политикой и операционной моделью банка.
